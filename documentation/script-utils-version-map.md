# `@cosyte/script-utils`: which version first carries which capability

Pin an exact version of `@cosyte/script-utils` for the capability you are adopting, and read the
limit that travels with it before you do. Every row below names the first published version that
carries that capability and the exact specifier to write into a manifest, so an adopting repository
never has to discover the answer from the registry, and never has to write a range that quietly
stops moving.

started from), release sha `254ca68ffc81472e2595bbb3478f2108d8f93d95` (`Version Packages (#111)`,

## The capability map

Every specifier here is an exact version with no range operator, which is the only kind of reference
that cannot move underneath a consumer.

| capability                  | what it is                                                         | first published in | pin this specifier           | in a manifest                     |
| --------------------------- | ------------------------------------------------------------------ | ------------------ | ---------------------------- | --------------------------------- |
| root entry point (`.`)      | `isCliEntrypoint(moduleUrl)`, the entry-point guard                | `0.0.1`            | `@cosyte/script-utils@0.0.1` | `"@cosyte/script-utils": "0.0.1"` |
| `./phi-scan`                | `runPhiScan(config)` and `exemptsMarkdown(relPath)`, the PHI gate  | `0.0.2`            | `@cosyte/script-utils@0.0.2` | `"@cosyte/script-utils": "0.0.2"` |
| `./internal-refs`           | `runInternalRefsScan(config)`, the internal-reference gate         | `0.1.0`            | `@cosyte/script-utils@0.1.0` | `"@cosyte/script-utils": "0.1.0"` |
| `./attw`                    | `runAttwGate(options)`, the shared `attw` publish gate             | `0.1.0`            | `@cosyte/script-utils@0.1.0` | `"@cosyte/script-utils": "0.1.0"` |
| packed `check-no-emdash.sh` | the one em-dash gate implementation, executed rather than imported | `0.1.0`            | `@cosyte/script-utils@0.1.0` | `"@cosyte/script-utils": "0.1.0"` |

A row names the EARLIEST version that carries its capability, which is not always the version you
want. An adoption that needs more than one capability pins the highest specifier among the rows it
needs, so anything reaching `./internal-refs`, `./attw` or the packed gate pins
`@cosyte/script-utils@0.1.0`. That is also the current `latest`.

### The limit beside each capability

Stated here rather than in a footer, because a limit a reader has to go and find has been marketed
around.

- **Root entry point.** A bare `import ... from "@cosyte/script-utils"` resolves through
  `node_modules`, so a gate that runs BEFORE `pnpm install` cannot use the bare specifier and must
  import a vendored copy by relative path instead. Installing the package does not give a
  pre-install gate that property. `isCliEntrypoint` has no options and cannot be overridden.
- **`./phi-scan`.** The engine's cross-cutting detection floor gains patterns as escapes are found,
  and a new pattern is a new red in a consumer that was passing. Pin an exact version if a green
  commit gate matters more to you than a new detection. The `runPhiScan` option surface is still
  moving. A caller can widen what is scanned and can add detection; it cannot subtract either the
  detection floor or the completeness rule that refuses a run which enumerated a target and never
  read it.
- **`./internal-refs`.** The same bargain: the canonical rule set, the self-test floor and every
  completeness refusal are not caller inputs, and an option that reaches for one of them is refused
  by name. So is an option the gate has never heard of, because an ignored setting reads from the
  caller's side exactly like an honoured one.
- **`./attw`.** The narrowest bargain of the four. The caller supplies `callerUrl` and may supply
  arguments to forward, but the forwarded set is an allow-list of two (`--profile` with its value,
  and `--no-definitely-typed`). Widening it is an edit inside the package, not a caller option.
- **Packed `check-no-emdash.sh`.** It is a file, not a subpath, so it is absent from the `exports`
  map: nothing imports it, a repository EXECUTES it as
  `bash node_modules/@cosyte/script-utils/check-no-emdash.sh`. A repository narrows WHAT IS SCANNED
  through a tracked `scripts/check-no-emdash.exclude` at its own top level, and nothing narrows WHAT
  IS MATCHED. The packed copy is build output regenerated by `scripts/pack-emdash-gate.mjs`, so it
  is not in the package directory in a checkout; the copy of record is `scripts/check-no-emdash.sh`
  at the repository root.
- **The `0.1.x` line as a whole.** [ADR 0002](decisions/0002-the-0-1-0-version-line.md) settles the
  surface, not the software: these entry points are the ones consumers should pin, and a removal or
  a rename from here on is recorded as a breaking change. It is not a `1.0.0` stability promise, and
  pre-`1.0.0` semver still permits a breaking change in a minor bump.

## An adopter on `^0.0.2` does not resolve this release

This is break candidate BC-2 in [the release audit](release-0.1.0-audit.md), and it is the one thing
an adoption has to act on rather than read.

npm's caret rule treats every `0.0.z` release as its own major, so `^0.0.2` matches `0.0.2` and
nothing above it. A repository carrying `"@cosyte/script-utils": "^0.0.2"` therefore keeps resolving
`0.0.2` after this release and never reaches `0.1.0`. It does not fail; it silently stops moving,
which is the harder failure to notice. Measured, not asserted:

```sh
npm view "@cosyte/script-utils@^0.0.2" version
0.0.2
```

`^0.0.2` is named here as the specifier an adopter CARRIES TODAY, never as one to pin. The remedy is
one edit per dependant, to an exact version from the table above.
`scripts/parser-template/package.json` still carries the old ranges deliberately: widening the
scaffold reaches every future parser repository and is a separate change, which is why the audit
dispositions BC-2 as `deferred`.

## How to re-derive every row

Nothing here is inferred. `exports` fixes the three subpath rows and the tarball listing fixes the
packed gate row, because the `files` field is not preserved in registry metadata.

```sh
npm view @cosyte/script-utils versions --json          # ["0.0.1","0.0.2","0.1.0"]
npm view @cosyte/script-utils dist-tags --json         # {"latest":"0.1.0"}
npm view @cosyte/script-utils@0.0.1 exports --json     # "." only
npm view @cosyte/script-utils@0.0.2 exports --json     # "." and "./phi-scan"
npm view @cosyte/script-utils@0.1.0 exports --json     # adds "./internal-refs" and "./attw"
npm pack @cosyte/script-utils@0.0.2 --dry-run          # 8 files, no check-no-emdash.sh
npm pack @cosyte/script-utils@0.1.0 --dry-run          # 13 files, check-no-emdash.sh among them
```

The packed gate is the canonical bytes rather than a fork, which `--self-id` makes checkable by a
command instead of by reading two files. The copy inside `@cosyte/script-utils@0.1.0` and
`scripts/check-no-emdash.sh` at the release sha report the same sha256,
`df1024aee0d7d02fba2f562cacf79228ff34e6b9fb141bf5f79e363ac10c4000`:

```sh
bash scripts/check-no-emdash.sh --self-id
bash node_modules/@cosyte/script-utils/check-no-emdash.sh --self-id
```

The release reached the registry through the gated `publish` job and nothing else, which the npm
provenance attestation on the published version is the evidence for:

```sh
npm view @cosyte/script-utils@0.1.0 dist.attestations --json
```
